# Application interaction logs

The navbar's Logs page provides date/time in the browser's local time zone, interaction type, details and the initiating user's name/email. Customers read only their own rows. Administrators read all rows and receive a user dropdown, defaulting to All users, on the left of the table. The right-hand search matches only interaction_type, case-insensitively; it does not search names, emails or details. Literal percent/underscore characters are escaped.

The API serves 25 rows at a time, newest first with an ID tie-breaker. Pagination retains the first response's timestamp cutoff, preventing new events from moving rows between pages. Refresh and changing either filter restart at page one with a fresh cutoff. The table has a contained scroll area, sticky headers and horizontal scrolling on small screens. Navigation collapses below 1024px to accommodate the additional link.

Events include login/logout, email authentication callbacks, successful/failed profile updates, page views, button/link clicks, control changes, account/manual-transaction CRUD, transfer completion/edits/reversals, assistant requests, financial reads, refresh checks and log-page reads. API request events include response status, so an attempted request is distinguishable from a completed banking operation. Browser-reported events are marked as such and may be incomplete if JavaScript or networking is unavailable. Failed browser log submissions show an application warning.

Banking completion events are inserted by database triggers in the original mutation transaction; rollback removes them, and idempotent retries do not duplicate completion events. Request/UI entries for separate retries still appear. Auth changes use Supabase Auth's separate service; their log write follows the successful action. Auth, UI and request logging is best effort with a five-second timeout and a sanitized activity_write_failed server error if unavailable. A completed operation is never presented as failed solely because its auxiliary log write failed. Anonymous/failed sign-in attempts have no verified initiator and are not attributed to a customer here; Supabase Auth maintains its own audit records.

Logging starts when this feature is installed. Earlier interactions are not reconstructed, and no fabricated historical events are seeded. The hosted verification records real test interactions, retained as part of the demo history, without moving funds. Passwords, tokens, raw assistant prompts, form values, IP addresses and URL query strings are not captured. Profile logs list field names, not their values. Banking logs can contain transaction amounts, account names and record IDs, which the requested admin log access intentionally makes visible across users.

The eighth migration, 202610060001_activity_logs.sql, is applied to the configured Supabase sandbox. It creates append-only activity_logs, owner/admin SELECT RLS, active-session enforcement, transactional triggers and an admin-only user-list RPC. Admin status comes from protected auth.users metadata, not editable user metadata or stale JWT role claims. Authenticated clients cannot insert/edit/delete rows directly or call the trusted record_activity RPC; the browser endpoint permits only explicitly marked page/UI event types and derives identity from the session. Service-role logging is server-only and has no table update/delete permission. Actor identity snapshots remain in history after a user's profile changes.

SUPABASE_SERVICE_ROLE_KEY is required on the app server for auth/UI/request logging. Keep it out of NEXT_PUBLIC_ variables and browser bundles. Apply the migration before deploying the app. Do not rerun it on the configured project. Admin filtering explicitly casts Supabase Auth's varchar email column to text; isolated tests model that actual column type.

Verification: npm test covers API ownership, type-only search, pagination input, spoof rejection, origin checks and request sanitization. npm run test:database checks real RLS, role demotion, logout replay, immutable writes, rollback, retry-safe events and stable pagination. With a production preview on localhost:3100, npm run verify:logs exercises the configured sandbox using all three demo identities, temporarily edits/restores one account name, and confirms retry-safe completion logs without changing balances. npm run verify:security audits both /api/logs methods and the protected /logs HTML/RSC page.
